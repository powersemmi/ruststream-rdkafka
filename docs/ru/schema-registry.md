# Schema Registry

Установки Kafka, стандартизованные на Confluent Schema Registry, одевают полезную нагрузку в
формат передачи Confluent - нулевой магический байт, четырёхбайтный идентификатор схемы со
старшим байтом впереди, затем закодированное значение, - а сами схемы держат в реестре. Фича
`schema-registry` покрывает обе половины, и обращаться с ними можно двумя способами. **Берите в
первую очередь кодек.**

**Кодек** помещает схему туда, где и место сериализатору. `AvroCodec` держит схему, обработчик
принимает модель и возвращает модель, и ничто про формат передачи не появляется в сигнатуре - для
этого кодек и нужен, и поэтому он единственный способ читать и писать полезную нагрузку Avro или
JSON Schema. Avro встаёт в эту позицию в точности: это формат, ведомый схемой, с интерфейсом serde;
полезная нагрузка JSON под конвертом - это собственный `JsonCodec` ядра внутри `SchemaFramed`.

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_avro_codec.rs:handler"
```

**Перекодирование** преобразует на краях брокера, поэтому обработчики держат обычные модели serde
на кодеке по умолчанию и формы передачи не видят никогда. Это путь совместимости: верный выбор
для сервиса, которому нельзя нести ни сгенерированные типы, ни модели, выведенные из Avro, - ценой
одного прохода через JSON на сообщение и потери разрешения схем, потому что у обработчика на JSON
нет схемы читателя, на которую можно было бы разрешать.

Друг с другом на одном брокере эти два не смешиваются.
`KafkaBroker::schema_registry(registry)` привешивает перекодирование к каждой подписке этого
брокера, поэтому кодеку на нём достался бы JSON; кодек берёт вместо этого
`KafkaBroker::schema_prefetch(..)`, который разрешает схемы, не трогая полезную нагрузку.

Protobuf - не третий выбор. Сообщение `prost` не является типом serde, поэтому в позицию кодека
оно не встанет никогда, и его полезная нагрузка передаётся самим конвертом Confluent - в сигнатуре
обработчика или на сгенерированном типе. Этот путь описан ниже, в разделе
[Конверт Protobuf](#the-protobuf-envelope).

## До чего дотягивается каждый формат {#what-each-format-reaches}

Пути покрывают три формата неодинаково. Один пробел вынужден системой типов и не закроется
никогда; остальные - недоработки, и таблица помечает, что есть что, вместо того чтобы оставлять
читателя догадываться.

| | Avro | JSON | Protobuf |
| --- | --- | --- | --- |
| Кодек | `AvroCodec::local`, `AvroCodec::registry` | `SchemaFramed<JsonCodec>` | вынужденный пробел, см. ниже |
| Конверт в сигнатуре | одни только типы конверта | одни только типы конверта | `protobuf::decode_framed`, `protobuf::Subject` |
| Обработчик над самим сообщением | кодек | кодек | `#[wire(..)]` + `ProtobufFrame` |
| Перекодирование | да | да | да |
| Схема читается с типа | `AvroSchema` | `schemars::JsonSchema` | **нет** |
| Субъект регистрируется с типа | `register_avro::<T>` | `register_json::<T>` | **нет** |
| Ссылки на схемы (`import`) | неприменимо | неприменимо | **не разрешаются** |
| Субъекты разрешаются при `connect` | кодек | кодек | вынужденный пробел |
| `MissingSubject` | кодек | кодек | вынужденный пробел |
| `check_compatibility` на старте | кодек | кодек | вынужденный пробел |
| Схема писателя разрешается на каждую доставку | кодек, которому она нужна | не нужна | не нужна |
| Общий кеш идентификаторов и субъектов | все пути | все пути | все пути |

**Вынужденный пробел.** Protobuf никогда не сможет быть кодеком. Дело в сигнатуре
`Codec::encode<T: Serialize>`: сообщение `prost` не является типом serde, поэтому в позицию кодека
оно не встаёт вовсе - конверт остаётся его единственным домом, и это свойство формата, а не
недоделанный угол. Каждая строка Protobuf с надписью «вынужденный пробел» - это тот же факт на шаг
дальше: `SchemaPrefetch` прогревает то, что зарегистрировал кодек, а без кодека прогревать нечего.

Стоит этот пробел меньше, чем кажется, потому что строка под ним заполнена. *Результат*, который
даёт кодек, - обработчик над обычными типами, без формы передачи в сигнатуре - Protobuf получает
другой дорогой, описанной в разделе
[Protobuf без конверта в сигнатуре](#protobuf-without-the-envelope-in-the-signature). Не получает
он машинерию предвыборки, которая держится на самой позиции кодека.

**Почему в строках про предвыборку написано «кодек», а не «Avro».** В этой машинерии нет ничего
только для Avro. `MissingSubject`, разрешение субъектов при подключении и проверка
совместимости на старте заданы на `SchemaPrefetch` и применяются к тому, что зарегистрировал кодек,
поэтому JSON под `SchemaFramed` получает их сегодня ровно так же, как Avro, - включая
`AutoRegister`, который кладёт обратно JSON Schema, выведенную через `schemars`.

**Protobuf отвечает на тот же вопрос конструктором, а не политикой.** `MissingSubject` у
`protobuf::Subject` нет, потому что он ему не нужен: `resolve` - это `Refuse`, а `pinned` - ни то
ни другое. Выбор делается там, где пишется код, а не значением, прочитанным при подключении, и эта
форма лучше - так что закрывать здесь нечего. Не хватает только пары к `AutoRegister`, и это уже
недоработка ниже, а не отсутствующая политика.

**Две настоящие недоработки, обе про Protobuf, обе - одна работа.** Тип Protobuf не может отдать
собственную схему, поэтому сервис пишет свой `.proto` дважды - один раз файлом, который компилирует
`prost-build`, и один раз строковым литералом для регистрации, - и ничто эти копии не связывает;
поэтому `protobuf::Subject::register` и нет. И ничто здесь не разрешает ссылки на схемы в
реестре, поэтому `.proto`, который импортирует что-то, чего в скомпилированном пуле ещё нет,
недостижим: стандартные типы `google/protobuf/*` разрешаются, `confluent/*` (которые сам реестр
считает всегда доступными) - нет, а любой ваш собственный импорт требует поля `references`, которое
крейт никогда не пишет и не читает.

## Кодек {#the-codec}

Источник схемы - часть кодека, и таких источника два.

`AvroCodec::local(schema)` закрепляет одну схему: при передаче идёт голое значение, без конверта,
без реестра и без ввода-вывода где бы то ни было на пути - это тема с фиксированной схемой и любой
модульный тест.

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_avro_codec.rs:local"
```

`AvroCodec::registry(&prefetch)` говорит на формате передачи Confluent, а `register::<T>(subject)`
сообщает, что он публикует: при кодировании каждое значение получает конверт с идентификатором
субъекта своего типа, а при декодировании каждая доставка читается схемой писателя, названной в
конверте этой доставки, - поэтому продюсер, оставшийся на старой версии, остаётся читаемым.

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_avro_codec.rs:wiring"
```

`SchemaPrefetch` - асинхронная половина, и существует она потому, что `Codec` синхронен с обоих
концов, а обращение к реестру - нет. Свести их внутри `encode` или `decode` нельзя: блокировать
рабочий поток рантайма из синхронной функции - не вариант, а угадывать схему - порча данных.
Поэтому обращения переехали в два места, которые и так асинхронны и и так знают, когда им нужно
произойти: в `connect` брокера - за субъектами, под которыми публикуют кодеки, и в путь доставки -
за схемой писателя, названной в пришедшем конверте. Поэтому несуществующий субъект выясняется,
пока приложение стартует, а не при первой публикации, а идентификатор, который предвыборка не
смогла разрешить, становится ошибкой декодирования, которую завершает политика отказа подписки, и
никогда - молчаливой догадкой.

### Регистрация относится только к стороне публикации {#registration-is-the-publish-side-only}

**Один кодек и столько типов сообщений, сколько смонтирует через него роутер.** Регистрация
сообщает, под каким субъектом обёрнуты значения типа, а декодированию из этого не нужно ничего:
схема писателя берётся из идентификатора в конверте, поэтому подписка с пятью типами декодирует
все пять через кодек, которому не сказали ни про один. Эта асимметрия и есть причина, по которой
один кодек обслуживает целую область; она же объясняет, почему `register` относится к половине
публикации, а на половине чтения ему ничто не соответствует.

Субъект ищется на каждую публикацию по **имени, которое даёт типу значения serde**. Очевидным
ключом был бы `TypeId`, и он недоступен: ему нужно `T: 'static`, а `Codec::encode` ограничивает
`T` только `Serialize`. При этом каждый выведенный `Serialize` отдаёт имя в `serialize_struct` до
того, как тронет хоть одно поле, поэтому пробующий сериализатор читает его и на этом
останавливается. Ключ верен и по существу: это то же имя, которое `AvroSchema` записывает в запись
Avro, и его же читает регистрация, когда у неё есть тип, но нет значения. `std::any::type_name`
намеренно не используется: стандартная библиотека не обещает для него ни уникальности, ни
стабильности.

Два зарегистрированных типа с одним именем serde сделали бы публикацию неоднозначной, поэтому
такое **отклоняется при регистрации**, до запуска приложения. Дайте одному из них отдельное
`#[serde(rename = "..")]`.

Что остаётся в цене: тип, который вы забыли зарегистрировать, - это **ошибка во время выполнения
при первой его публикации**, называющая этот тип и перечисляющая те, что у кодека есть. Сделать её
ошибкой компиляции значило бы нести список сообщений в типе кодека, а это и есть форма «параметр
типа на каждую точку монтирования», ради ухода от которой этот дизайн и существует.

### Схема читателя - это настройка, а не требование {#a-reader-schema-is-tuning-not-a-requirement}

`resolve_onto(schema)` включает собственное разрешение схем Avro, поэтому поле, которого у писателя
никогда не было, заполняется из умолчания схемы читателя. Оно действует на **каждую** доставку,
которую декодирует этот кодек - у декодирования есть тип, но нет значения, так что ключа, по
которому выбирать схему читателя на тип, просто нет, - и это делает его настройкой для кодека,
который читает один тип. Кодек, обслуживающий несколько, пользуется вместо этого `#[serde(default)]`
на стороне Rust, и то же самое покрывается по полям.

### Когда субъекта больше нет {#when-the-subject-is-gone}

Субъект могут удалить из реестра, пока продюсер работает, поэтому реакция - это политика, а не
готовый ответ: `SchemaPrefetch::on_missing_subject`, enum с умолчанием **`Refuse`**.
Создавать субъекты в чужом реестре побочным эффектом старта хуже, чем не стартовать.
`AutoRegister` кладёт обратно собственную схему типа и предупреждает, а `PublishUnframed` пишет
голое значение и предупреждает. Каждое предупреждение называет субъект, формат и схему, потому что
голое «схема отсутствует» не говорит эксплуатации ничего.

Словарь взят у Confluent намеренно. Их сериализаторы покрывают эту область тремя настройками, и
две из них описывают обычный путь этого крейта, а не политику: кодирование всегда пишет схемой,
названной в идентификаторе конверта, то есть `use.latest.version`, а `check_compatibility` - это
`latest.compatibility.strict`. Для enum остаётся вопрос, на который те две отвечают вместе: когда
субъекта нет вовсе, продюсер его создаёт (`AutoRegister`, их `auto.register.schemas=true`),
отказывается (`Refuse`, их `auto.register.schemas=false` вместе с `use.latest.version=true`) или
обходится без него (`PublishUnframed`, у которого соответствия у Confluent нет). Это enum, а не
три булевых флага, потому что флаги не независимы - `use.latest.version` ничего не значит, пока
включена автоматическая регистрация, - а комбинацию, которая ничего не значит, enum и оставляет
непредставимой.

`check_compatibility` включён по умолчанию, как и у Confluent, и он закрывает пробел, который
прежний дизайн с субъектом на типе закрыть не мог: при `connect` схема каждого зарегистрированного
типа сверяется с версией, которая уже лежит в его субъекте, и разошедшаяся модель останавливает
приложение с собственным разбором различий от реестра, вплоть до поля, а не всплывает потом
консьюмером, который не может прочитать записанное.

Два вида удаления различаются, и это проверено на живом реестре, а не принято на веру. **Мягкое**
удаление прячет субъект - его `versions/latest` отвечает 404, - но `GET /schemas/ids/{id}` всё ещё
возвращает схему, поэтому **консьюмеры продолжают работать**, и застревает только продюсер.
**Окончательное** удаление убирает и идентификатор, и тогда запись, называющую его, не декодирует
уже ничто: здесь консьюмеру не поможет никакая политика, потому что схемы нет ни для кого.
Повторная регистрация потом выпускает *новый* идентификатор, поэтому записи, уже лежащие в теме,
остаются непрочитанными.

Здесь путь кодека и `SchemaFrame` расходятся, и намеренно. Слой перекодирования считает субъект,
которого реестр не знает, признаком «эта тема не связана с реестром» и публикует нетронутым,
потому что там условие действительно неоднозначно: он разрешает субъекты для каждой темы, куда
публикует приложение, а большинство из них с реестром и не связаны. На пути кодека неоднозначности
нет: запись `register::<Order>("orders-value")` *объявляет* тему связанной с реестром, поэтому
отсутствующий субъект - аномалия, а не обычная тема, и умолчание об этом говорит.

### JSON устроен так же {#json-takes-the-same-shape}

`SchemaFramed::new(&prefetch, JsonCodec).register::<Order>("orders-value")` - тот же билдер над тем
же ассоциативным массивом по именам и по той же причине. Регистрация снимает JSON Schema типа через
`schemars`, поэтому `AutoRegister` есть что положить обратно.

### Реестр называют один раз {#naming-the-registry-once}

Реестр называют в приложении дважды и ни разу в точке монтирования: один раз при построении
предвыборки и один раз при привешивании её к брокеру. Каждый кодек изготавливается из этой одной
предвыборки, поэтому от монтирования к монтированию меняется субъект - то, что и правда
различается.

Область действия здесь - собственный каскад кодеков ядра, и он уже делает то, что нужно схемам:
кодек, заданный на область брокера, покрывает всех её обработчиков, а смонтированный внутри роутер
перекрывает его для своих обработчиков. Побеждает самый частный, ровно как для любого
другого кодека.

Один кодек теперь обслуживает целую область, поэтому перекрытие нужно для настроек, которые
разделить нельзя. Яснее всего это со схемой читателя: она действует на каждую доставку, которую
декодирует её кодек, поэтому кодек с такой схемой может обслуживать только один читаемый тип, и
обработчик, которому нужно разрешение Avro, получает собственный кодек в собственном роутере, а
кодек области продолжает обслуживать остальных. Поддерево, публикующее в другой реестр или под
другой политикой `MissingSubject`, изготавливается тем же способом.

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_avro_codec.rs:cascade"
```

Уровня всего приложения нет, потому что ядро задаёт область кодека на брокере и на роутере, а
реестр в любом случае вещь на кластер. Чего ядро не предлагает, так это *частичного* перекрытия -
«взять кодек области и поменять одну настройку», - потому что кодек для него непрозрачное значение.
Этим перекрытием и служит предвыборка, изготовившая второй кодек, и стоит оно одну строку.

### Эволюция схемы {#schema-evolution}

Чтение значения его схемой писателя восстанавливает то, что писатель записал, и не больше. Поле,
которого у писателя никогда не было, заполняется из умолчания схемы *читателя*, и это собственное
разрешение схем Avro: `resolve_onto(schema)` называет схему, которую ожидает этот консьюмер. Без
неё модель с полем, которого у писателя нет, не десериализуется, и это честный исход: значения при
передаче действительно нет.

### JSON под конвертом {#json-under-the-envelope}

`SchemaFramed::new(&prefetch, JsonCodec)` - это реестровый кодек для JSON. Конверт здесь отделим,
потому что документ JSON самоописателен: идентификатор говорит, какой схеме документ заявляет
соответствие, а разбирается документ и без него. Значение Avro нельзя прочитать без схемы,
названной его идентификатором, поэтому `AvroCodec` владеет своим конвертом, а не пользуется этой
обёрткой; граница между ними проходит по этому свойству, а не между двумя форматами.

Локального кодека JSON нет, потому что ему нечего делать: локальная JSON Schema была бы схемой, к
которой кодек никогда не обратится, поэтому локальный случай JSON - это собственный `JsonCodec`
ядра.

Обёртка ставит конверт и не проверяет. JSON Schema в реестре - это контракт совместимости, который
реестр держит между версиями, и сверка каждого сообщения с ней потребовала бы валидатора JSON
Schema и расходов на каждую доставку; поэтому и собственный сериализатор Confluent делает
эту сверку необязательной. Проверка принадлежит внутреннему кодеку, а внутренний кодек называют
прямо в точке вызова: передайте туда проверяющий кодек вместо обычного.

### Что клиент запоминает {#what-the-client-remembers}

`SchemaCachePolicy` следует свойству реестра, а не предпочтению: **идентификатор схемы неизменен**.
Идентификатор назначается на каждое различное определение схемы, глобально и по содержимому,
поэтому новая версия субъекта выпускает новый идентификатор и навсегда оставляет старый
разрешающимся в старую схему, тогда как *последняя версия* субъекта смещается, как только кто-то
зарегистрирует новую.

Поэтому двум половинам нужно противоположное обращение. Записям по идентификатору нужно
ограничение по количеству и не нужен срок годности - TTL над ними мог бы вызвать только повторную
загрузку тех же самых байтов, - и ограничение важно, потому что консьюмер встречает по
идентификатору на версию писателя, а это немного в здоровой топологии и неограниченно в сломанной.
Записям по субъекту нужен срок годности и не нужно ограничение по количеству. Собственные клиенты
Confluent по той же причине распространяют свой `latest.cache.ttl.sec` только на кеши последних
версий. `SchemaCachePolicy::Disabled` выключает кеш целиком - это настоящая настройка, а не
переодетый нулевой TTL, и следствие у неё такое: синхронные кодеки, которые читают кеш и не могут
дождаться промаха, под ней не работают.

## Клиент {#the-client}

`SchemaRegistry::new` запоминает URL и не отправляет запроса до первого обращения. На клиенте можно
задать базовую или bearer-аутентификацию, а HTTPS идёт через rustls. Все клоны клиента читают и
пишут один кеш, поэтому идентификатор схемы или субъект забирается по сети один раз на процесс.

У каждого запроса к реестру есть срок, по умолчанию десять секунд, и его меняют через
`request_timeout`. Доставка или публикация ждёт обращения, поэтому этот срок и ограничивает реестр,
который принял соединение и замолчал. По истечении срока запрос возвращает ошибку, и оба края
обходятся с ней как с любой другой ошибкой реестра.

## Конверт Protobuf {#the-protobuf-envelope}

Конверт - это тип байтового пути с обоих концов: `IncomingFrame` приходит по пути `Deserialized`
ядра, `OutgoingFrame` уходит по `Serialized`, и кодек не разрешается ни там, ни там. Это то место,
где сообщение `prost` жить может, а кодек до него не дотягивается: пути ядра выбираются по типу и
заказаны для типов, которые типами serde *не* являются (`MessageWire`, `ReplyShape` и `Input`
реализованы бланкетно для любого значения `Serialize` / `DeserializeOwned`) - поэтому
`#[wire(prost)]` для сообщения `prost` работает, а равнозначного `#[wire(avro)]` существовать не
может.

Чтению реестр не нужен вовсе. Путь индексов сообщения в конверте говорит только о том, какое
сообщение схемы было записано, а читающий тип уже решил, какое он читает, поэтому
`protobuf::decode_framed` - обычный синхронный вызов. Разрешает что-либо только сторона публикации,
и разрешает один раз, на старте, поэтому сама публикация не делает ввода-вывода, а отсутствующий
или несовместимый субъект валит старт приложения, а не его первое сообщение:

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_lanes_testing.rs:handler"
```

`Subject::resolve` ищет идентификатор, ничего не регистрируя, - этого же хотят установки, где
продюсерам нельзя создавать схемы (собственная рекомендация Confluent, с выключенным
`auto.register.schemas`); `Subject::pinned` берёт идентификатор, который сервис уже знает, - для
закреплённого развёртывания, инструмента повтора или теста, перед которым реестра нет.

Сами типы конверта никакого знания о схемах не несут, поэтому они же остаются сырой формой для
редкого обработчика, который раскладывает по идентификатору схемы или пересылает дальше кадры,
которые никогда не декодирует, в любом формате.

## Protobuf без конверта в сигнатуре {#protobuf-without-the-envelope-in-the-signature}

Обработчик на путях выше видит конверт, потому что сам об этом попросил. Это не обязательно:
сгенерированный тип может нести конверт на собственных путях передачи, и тогда обработчик -
обычная функция над обычными типами, ровно как на кодеке Avro.

Две половины несимметричны, и понимание почему делает эту форму одним целым, а не двумя вещами.
**Чтению реестр не нужен**, поэтому оно может происходить в типе: модель совместимости Protobuf -
это собственная модель его формата передачи (поля адресуются тегами, неизвестное читателю поле
сохраняется как неизвестное, ненаписанное писателем берёт умолчание), поэтому доставка
декодируется в собственный сгенерированный тип читателя, а всё, что конверт ставит перед
сообщением (магический байт, идентификатор, путь индексов сообщения), разбирается, ни у кого
ничего не спрашивая. **Записи нужно одно число**, идентификатор схемы субъекта, а значение достать
его не может: `Serialized::wire_bytes` синхронен, и всё, чем он располагает, - это `&self`. Путь
публикации может, потому что знает тему-адресата, а она и называет субъект.

Поэтому тип разделяет свои пути передачи - `prost` пишет сообщение, крейт читает конверт, - а
идентификатор и путь индексов ставит на выходе собственный издатель ответа.

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_protobuf_plain.rs:types"
```

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_protobuf_plain.rs:handler"
```

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_protobuf_plain.rs:wiring"
```

Обработчик возвращает свой ответ и больше ничего: ни параметра-слота, ни `publish().await`, ни
ветки с ошибкой в теле. Тип ответа тоже не объявляет собственного адресата, потому что адрес берётся
из клаузы `publish("confirmations")`; ему достаточно `#[derive(Serialized)]` и кодирующей половины
`#[wire(..)]`. Реестр называют один раз, в точке монтирования, в политике.

`KafkaPublish::framed(&registry)` работает везде, где называют политику публикации, включая слот
`Out`, поэтому обработчик, публикующий несколько сообщений, одевает их все одинаково.

### Настроить один раз на всё приложение {#setting-it-once-for-a-whole-app}

`ProtobufFrame` - тот же конверт в виде `publish_layer`, для приложения, которому иначе пришлось бы
повторять политику в каждой точке монтирования:

<!-- inline-rust: one line of wiring; the compiled example shows the mount-site form, which is the one to reach for first -->
```rust
RustStream::new(info).publish_layer(ProtobufFrame::new(registry))
```

Конверт он ставит только тогда, когда субъект темы-адресата зарегистрирован **и держит схему
Protobuf**, а всё остальное пропускает нетронутым - тему без субъекта и тему, чей субъект Avro или
JSON. Именно поэтому одно приложение держит сразу кодек Avro, кодек JSON и Protobuf при
слое, установленном на всё приложение; по этой же причине слой снисходителен там, где политика
нет: слой видит каждую тему, куда публикует приложение, и большинство из них не Protobuf, тогда как
названная в точке монтирования политика *объявляет* этот один адресат связанным с реестром, поэтому
отсутствующий субъект там - аномалия, и публикация падает. Тот же довод приводит умолчание `Refuse`
у `MissingSubject` на пути кодека.

Одного слой не может: **он никогда не видит ответ из `publish(..)`**. Ядро намеренно направляет
байт-в-байт ответ прямо его связанному издателю, чтобы значение, владеющее своими байтами, ушло
ровно таким, каким его записали, - поэтому форма ответа берёт политику, а слой покрывает
публикации, уходящие через слоты и через издателей, которых точка монтирования не называла. Эти
двое складываются, а не конфликтуют: кто отработал первым, тот и одел полезную нагрузку, а второй
находит конверт на месте и не трогает его.

Полезная нагрузка, у которой конверт уже есть, проходит насквозь на обоих путях, поэтому обработчик,
одевший своё сообщение через `Subject::frame`, не одевается дважды. Проверка точная, а не
догадливая: голое сообщение `prost` начинается с тега поля, чей номер не меньше 1, поэтому его
первым байтом никогда не бывает нулевой магический байт.

Ни то ни другое не заменяет `SchemaFrame`: контракт того слоя - «эта полезная нагрузка -
документ JSON, перекодируй её в формат субъекта», а этих - «эта полезная нагрузка уже и есть
значение, надень конверт».

### Какое сообщение схемы {#which-message-of-the-schema}

Путь индексов в конверте говорит, какое сообщение было записано, поэтому он обязан указывать ровно
то сообщение, которому соответствует публикуемый тип. И политика, и слой по умолчанию берут первое
сообщение верхнего уровня
схемы - обычный случай, и именно его Confluent оптимизирует до одного нулевого байта, - поэтому
`.proto` с одним сообщением не требует ничего. Всё остальное закрепляют через
`.message(topic, "pkg.Message")`, тем же вызовом, который уже принимает `SchemaFrame`.

Субъект разрешается при первой публикации в каждый адресат и с этого момента кешируется. На старте
это произойти не может: политика могла бы сделать ввод-вывод, когда конструирует издателя на
подключённом брокере, но тема-адресат там неизвестна - она берётся из клаузы `publish(..)` точки
монтирования или из точки вызова публикации в слот, а ни того ни другого политике не передают.
Поэтому отсутствующий субъект всплывает неудавшейся публикацией, которую завершает политика отказа
обработчика.

### Для чего остаётся явный путь {#what-the-explicit-path-is-still-for}

`IncomingFrame` с `protobuf::decode_framed` и `protobuf::Subject` остались прежними и лишними от
этого не стали. Берите их, когда обработчику нужен **идентификатор схемы**: записать в лог, какая
версия произвела доставку, развести тему, несущую больше одной схемы, переслать дальше конверты,
которые он никогда не декодирует, - потому что это единственное, что декодирование за конверт
выбрасывает. `Subject` - ещё и путь продюсера вне конвейера публикации приложения (инструмент
наполнения, задание повтора, тест, перед которым реестра нет), где ставить конверт некому.

## Чтение: перекодирование на входе {#consuming-transcode-on-the-way-in}

`KafkaBroker::schema_registry(registry)` ставит клиента на край чтения: каждая подписка этого
брокера преобразует доставку в конверте в обычный JSON, прежде чем полезная нагрузка дойдёт до
кодека. Полезная нагрузка JSON Schema сохраняет свои байты и теряет конверт. Значение Avro или
Protobuf преобразуется через схему реестра, названную в его конверте, при включённой фиче этого
формата. Обработчики после этого - обычные подписчики на кодеке по умолчанию:

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_schema_registry.rs:handler"
```

Полезная нагрузка без конверта проходит нетронутой, поэтому тема, где смешаны записи в конвертах и
без, продолжает работать. Доставка, которую middleware преобразовать не смог, проходит
неперекодированной и с предупреждением: либо обращение к схеме вернуло ошибку, либо фича этого
формата выключена. Что будет с этой доставкой дальше, решает политика отказа при декодировании у
подписчика.

## Публикация: конверт на выходе {#publishing-frame-on-the-way-out}

`SchemaFrame` - это middleware публикации; его добавляют на всё приложение через
`RustStream::publish_layer`. Для каждой публикации, идущей через конвейер приложения, он разрешает
субъект темы-адресата и одевает полезную нагрузку из обычного JSON в **зарегистрированный формат**
этого субъекта: субъект JSON Schema сохраняет свои байты под конвертом, субъект Avro или Protobuf
преобразуется. Формат передачи темы решает реестр, и ни один издатель его не объявляет.

Субъект по умолчанию следует стратегии Confluent `TopicName`, `{topic}-value`. Соответствие меняют
через `subject_strategy` или закрепляют субъект одной темы через `subject(topic, subject)`.
Стратегии `RecordName` и `TopicRecordName` называют субъект по типу записи, а путь публикации его
не передаёт, поэтому субъект получается пустым или заканчивается дефисом. Обеим нужен субъект,
закреплённый на каждую тему.

Тема, чьего субъекта реестр не знает, публикуется нетронутой, поэтому одно приложение обслуживает
темы с реестром и без всякой настройки. `SchemaFrame` запоминает незарегистрированный субъект и
пишет о нём в лог один раз; субъект, зарегистрированный позже, начинает действовать после
перезапуска или явного `warm`.

Публикация, которую не удалось одеть, возвращает ошибку: либо обращение за субъектом вернуло
ошибку, либо схема субъекта отвергла полезную нагрузку. Публикующий обработчик тогда шлёт `nack`
своей доставке и просит повтор, поэтому неверно одетая запись в тему не попадает.

Субъект разрешается **лениво, при первой публикации** в его тему, поэтому сервису, чьи субъекты в
реестре уже есть, шаг на старте не нужен. Продюсер, который владеет своими схемами, регистрирует
их на старте, прямо из типа сообщения:

```rust
--8<-- "crates/ruststream-rdkafka/examples/kafka_schema_registry.rs:types"
```

Адресата объявляет тип ответа: `#[outgoing(name = "confirmations")]` называет тему, а подписчик
пишет `publish` без имени.

`register` отправляет определение, которое написали вы, и одинаковая схема сохраняет уже имеющийся
идентификатор. `register_json::<T>` выводит JSON Schema из типа через schemars, который крейт
реэкспортирует. `warm` не регистрирует ничего: он разрешает существующий субъект и кеширует его -
для установок, где продюсерам нельзя создавать схемы (`auto.register.schemas` выключен).

Каждый издатель, которого конструирует рантайм, публикует через конвейер приложения, поэтому
ответы, транзакционные издатели, издатели на партицию и конвейер exactly-once одеваются в конверт
без всякой настройки в точке монтирования. Издатель, которого вы сконструировали с подключённого
брокера сами, находится вне конвейера и публикует ровно то, что ему дали.

## Форматы на пути перекодирования {#formats-on-the-transcoding-path}

- **JSON** (одна фича `schema-registry`, на кодеке `json` по умолчанию): конверт надевается и
  снимается, сам документ остаётся нетронутым. Документ не сверяется с зарегистрированной схемой,
  поэтому действующий контракт - это тип обработчика.
- **Avro** (фича `avro`): значения преобразуются через схему реестра с обоих краёв.
  `register_avro::<T>` выводит схему из типа, а вывод `AvroSchema` реэкспортирован:

    ```rust
    --8<-- "crates/ruststream-rdkafka/examples/kafka_avro.rs:wiring"
    ```
- **Protobuf** (фича `protobuf`): сообщения преобразуются в JSON и обратно через дескрипторы,
  скомпилированные из исходника `.proto` в реестре. Стандартные типы доступны; ссылки на схемы
  реестра дальше них не разрешаются. Индексы сообщений читаются и пишутся с обоих краёв, поэтому
  вложенные схемы и схемы с несколькими сообщениями работают. Исходящее сообщение берёт первое
  сообщение верхнего уровня схемы; другое называют на каждую тему через
  `SchemaFrame::message("topic", "pkg.Message")`:

    ```rust
    --8<-- "crates/ruststream-rdkafka/examples/kafka_protobuf.rs:wiring"
    ```

Чем платят за перекодирование: один проход через JSON на сообщение в темах с реестром покупает
единую модель обработчика - та же структура, тот же кодек, любой формат передачи - и отдаёт то,
чего документ JSON унести не может. Типы Avro, для которых у JSON нет формы, его не переживают, а
значение, записанное под старой версией субъекта, декодируется, а не разрешается: обработчик видит
поля писателя, и схемы читателя, которая заполнила бы ненаписанное продюсером, нет. Берите этот
путь, когда сервис обязан держать обычные модели serde на теме, связанной с реестром; в остальных
случаях берите кодек.
