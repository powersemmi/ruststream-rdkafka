    基准测试¶

    英文版本为准

    本页译自英文，由模型翻译。若与英文原文存在差异，以英文原文为准。

    在 Kafka 客户端和你的代码之间，凡是夹在中间的东西都要在每条消息上花时间：订阅的流、归自己所有 的投递、解码、分发、ack。这一页说明它花了多少，参照物是同样的活用 rdkafka 手写一遍。

    同一个进程把每个场景跑三遍，三个循环之间只差一件事：由谁把投递送过来。其余一切都保持相同： 消费者属性、消费者组、提交模式、ack 的位置、解码成同一个类型、载荷字节、tokio 运行时和构建。这套 流程属于框架本身，写在 RustStream 基准测试页 上；这一页公布它在这台机器上得出的结果。

    数字¶

    三个交错轮次中的最佳值，括号里是中位的一轮。越大越好。

    表格由浏览器从上一次运行写下的文档读出，所以这一页上没有任何会过期的副本。

    三个被测量的列是同一个场景的三个循环。「裸客户端」直接驱动一个 librdkafka 消费者：在自己的循环里 接收、解码、存下偏移量。「适配层」只驱动这个 crate，不含它之上的任何东西：Broker 连上，主题描述符 打开一个订阅，循环从它给出的流里取投递、解码，然后 ack。「RustStream」是用户真正会写的服务：一个 #[subscriber] 处理器，以及围着它的 app。

    所以「适配层开销」就是这个 crate 自己的消费者在它所包装的客户端之上要付的代价，而这一列和「开销」 之间的差额，则是运行时在其上再加的代价。前一个数字由这个仓库负责。后一个属于核心，之所以也公布在 这里，是因为运行时如何与一个按批取回投递的传输相遇，这件事是关于这个 crate 的；运行时自身的代价， 以每条消息的指令数计，由核心在自己那一页公布。

    两行都是一个消费者通过一个消费者组读一个主题，区别只在于 ack 意味着什么。在自动提交下，已提交的 位置由 librdkafka 掌管，ack 只是知会。在 Commit::Tracked 下，每一次 ack 都存下一个偏移量，而 水位线永远不会越过仍在处理中的投递。

    适配层这一列付的主要是「投递归自己所有」的代价。这个 crate 交出去的是一条拥有自身的消息：消息体、 消息头、主题和分区。所以在任何人读到它之前，投递已经从客户端的缓冲区里复制了出来；手写的循环则 就地解码，直接读 librdkafka 借给它的缓冲区，一个字节也不复制。这正是这个 crate 做的取舍：归自己 所有的投递能活过轮询循环，代码因此可以 await、把活摊到工作分区上，以及稍后再确认。

    标着「受 Broker 限制」的一行，是裸客户端整趟都在等套接字的那一行。这由算术决定，不靠印象：循环 之外的一次探测测出一个请求和它的应答要多久，另一次探测数出 librdkafka 每条投递实际发出多少请求， 当两者之积达到实测每条消息用时的一半时，这一行就被标记。测到的往返时间公布在下面，算术可以自己 核对。

    同一次运行的机器可读形式在 benchmarks/results.json， 框架的站点用它拼出跨 Broker 的汇总表。

    crate 自身的代码¶

    第二张表是一条消息在服务线程上的开销，是数出来的，不是计时得来的：指令数由 callgrind 统计，内存分配 次数由 DHAT 统计。每个场景都是用户会写的那种服务，跑在 KafkaBroker 上，连的是同一个测试台：一个 消费者组读一个只有一个分区的主题，另一个线程在被测区段开始之前把主题灌满。服务线程做的一切都计入： 框架的分发、本 crate 的代码，以及本 crate 在这个线程上对 librdkafka 的调用。librdkafka 在自己的线程 上做的事不计入：拉取、消费者组协议、生产者发送记录以及投递报告。所以回复到 Broker 的往返不在它那 一行里，而服务线程发送回复、接收它的投递报告所做的工作在。

    指令数和分配次数都是稳态下每条消息的值：1000 次投递的运行和 2000 次投递的运行之间的斜率。最后一列 是启动服务、加入消费者组并处理第一次投递一次性付出的开销。这些数字是绝对值，框架自身的开销也算在 内；框架单独的开销由核心库在它的基准测试页面上公布。

    Broker 是真实的，所以同一个二进制文件多次运行，计数会有少许变化：服务线程多频繁地发现 librdkafka 的队列为空、或在等投递报告，取决于时机，而每次等待都要付出一次唤醒。同一个二进制文件跑三次，分配 次数完全相同；消费和批处理每条消息的指令数相差不到万分之一，回复最多相差百分之三。just bench-code 在分配次数超过场景声明的下限（三次运行中的最大值再加千分之一）时失败，指令数比对照的那次运行多出 百分之五以上也算失败：对照的是上一次运行，加上 --baseline=main 时是 main。改变开销的合并请求要 附上自己的数字。

    机器¶

    构建标志和数字一起公布，因为它们会改变这些数字。用 -C target-cpu=native 构建出的二进制给出的 结果，换一台机器就复现不了，所以这条 recipe 在构建前先把这个变量清空。

    这些数字不代表什么¶

    这里只有一个消费者、一个只有一个分区的主题、一个很小的消息体，以及一个跑在回环地址上的单节点 集群。它测的是一次投递在这个 crate 里的开销，不是 Kafka 能扛多少。这里的一行也不能拿去和另一个 Broker 公布的一行比较：不同的传输在每条消息上做的事并不一样。

    一次运行的测量窗口从第一次投递开始，到最后一次被解码为止，三个循环都是这样。偏移量在那之后才存 下来，所以一次运行携带的数百万次存储里的这一次，在哪个循环里都落在数字之外。

    多个分区的主题、一池工作分区、批处理器和事务流水线各自回答的是另一个问题，对比测试一个都没有测。 代码表在同一个测试台上统计了批处理器。

    这些数字是一台机器在某一天的快照。 它们由人手工重测，测量期间机器只跑这一项：这一页要讲的差值，比与其他任务共用的机器上的噪声还小。

    自己跑一遍¶

    just bench

    这条 recipe 从 docker-compose.test.yml 起停测试台，跑完两个场景，然后把测到的结果写回 docs/benchmarks/results.json。它要花十五分钟左右，并且需要整台机器。消息条数不是固定的：一次试探 运行会把它定下来，使得每一次被测量的运行在所在机器上都不短于五秒。

    just bench-code

    这条 recipe 起停同一个测试台，在 valgrind 下统计代码表，并重写同一份文档里的 code 部分。它要花 一两分钟，需要 valgrind 和基准测试运行器：cargo install --locked gungraun-runner --version =0.19.4。
